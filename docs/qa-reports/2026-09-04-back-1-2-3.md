## Constats

### [bloquant] BACK-3 : un `200` sans aucune vérification vaut « connecté »

`lib/ai-connection.ts:265` — `if (response.ok) return success();`. Le corps n'est
délibérément pas lu (motif légitime : OpenAI et DeepSeek recopient un fragment de clé dans
leurs erreurs), mais aucune autre preuve n'est exigée en échange : ni `content-type`, ni
longueur, ni rien.

Reproduction (sonde, `fetchImpl` injecté) :

- `new Response("<html>login</html>", { status: 200, headers: { "content-type": "text/html" } })`
  → `{"block":"ai","status":"success"}`
- `new Response(null, { status: 200 })` → `{"block":"ai","status":"success"}`

Ce que ça casse : un proxy d'entreprise qui intercepte le TLS (CA installée) et répond
`200` avec une page de connexion fait afficher « ✅ connecté » sur une clé jamais vérifiée ;
BACK-4 persiste `ai: connected`, FRONT-4 débloque « Terminer », et l'échec ne réapparaît
qu'à la première analyse, sans lien visible avec sa cause. Le cas est d'autant moins
théorique sur DeepSeek, dont le chemin n'est pas prouvé (`endpointProven: false`) : un
chemin faux renvoyant `200` serait annoncé comme un succès.

Les deux modules frères ferment exactement ce cas et le documentent comme tel
(`lib/jira-connection.ts:563-582`, message « unusable » ; `lib/figma-connection.ts:180-182`,
`looksLikeFigmaUser`). L'asymétrie n'est justifiée nulle part dans l'en-tête de
`ai-connection.ts`.

Correction minimale, sans lire le corps : exiger un `content-type` JSON avant `success()`,
et rendre l'indétermination explicite sinon. La valeur exacte de l'en-tête chez les six
providers n'a pas été sondée ici — à confirmer par sonde, comme le reste de la table.

### [à surveiller] Trois entrées aberrantes lèvent une exception, alors que les fichiers écrivent « ne lève jamais »

Sondes (valeurs typées `never` pour simuler un corps venu du réseau) :

| Appel | Résultat |
| --- | --- |
| `testAiConnection({ provider: "mistral", apiToken: "…" })` | `TypeError: Cannot read properties of undefined (reading 'buildTestRequest')` (`ai-connection.ts:195-196`) |
| `testAiConnection({ provider: "openai" })` (sans `apiToken`) | `TypeError: … (reading 'trim')` (`ai-connection.ts:186`) |
| `testJiraConnection({ email, apiToken })` (sans `instanceUrl`) | `TypeError: … (reading 'trim')` (`jira-connection.ts:159`) |
| `testJiraConnection({ instanceUrl, apiToken })` (sans `email`) | `TypeError: … (reading 'trim')` (`jira-connection.ts:257`) |
| `testFigmaConnection({})` | réponse d'erreur propre, `code: "invalid_token"` |

`lib/figma-connection.ts:283` est le seul des trois à se défendre (`credentials?.apiToken`
lu en `unknown`). Que la validation du corps de requête appartienne à la frontière HTTP est
un choix légitime et documenté — mais les JSDoc affirment l'inverse :
`jira-connection.ts:429` « tout échec — **y compris une entrée aberrante** — ressort en
`{ status: "error", message }` », `ai-connection.ts:180` « Ne lève jamais ». L'auteur de la
route lira ces phrases et n'écrira pas de `try/catch` : un provider hors liste rendra un
`500` nu, soit exactement le « crash serveur » que le critère d'acceptation de BACK-1
interdit. Aligner code et phrase, dans un sens ou dans l'autre, avant commit.

### [à surveiller] BACK-1 : le nom d'hôte saisi est recopié dans des messages destinés au disque

`lib/jira-connection.ts:52-57` (invariant 3 : « l'URL saisie n'est JAMAIS citée telle
quelle […] un utilisateur qui colle son jeton dans le champ URL par erreur ne doit pas le
voir écrit durablement sur disque ») contre `jira-connection.ts:371-395` et `493-547`, qui
citent `host` dans dix messages.

Reproduction : `instanceUrl = "https://ATATT3xFfGF0-SECRETTOKEN123"`, `fetch` en `ENOTFOUND`
→ `"Le domaine atatt3xffgf0-secrettoken123 est introuvable. …"`, avec `code:
"instance_unreachable"`. Ce message part vers `lastError.message` (BACK-4), sur disque, et
est relu à chaque `GET /api/settings`.

Portée réelle : étroite — un jeton collé sans schéma est rejeté avant tout appel, et il faut
que la saisie commence par `https://`. Mais l'invariant tel qu'écrit est faux, et c'est
l'invariant qui sera relu comme une garantie. Soit citer `host` seulement lorsqu'il ressemble
à un nom de domaine, soit corriger l'invariant pour dire ce qu'il fait vraiment.

### [à surveiller] Le contrat Jira n'est élargi qu'en entrée : `email` n'a aucun canal de sortie

`lib/types/settings.ts:82-86` rend `email` requis dans `JiraCredentials`, donc dans
`JiraSettingsUpdate` (l. 403-406) que BACK-4 persistera. Mais `JiraSettingsState`
(l. 328-333) ne porte que `instanceUrl` et `account` : `GET /api/settings` n'a aucun moyen
de rendre l'e-mail. Or le commentaire l. 307-309 justifie précisément la présence
d'`instanceUrl` par le besoin de FRONT-2 de pré-remplir le champ au retour sur l'écran.

Conséquence si rien n'est tranché : au rechargement, l'URL est pré-remplie, le champ e-mail
est vide, et l'utilisateur doit deviner quelle adresse avait été validée — un test au blur
sur le champ jeton échouerait alors en « Renseigne l'adresse e-mail associée à ton compte
Atlassian » sur une connexion pourtant valide.

`docs/api-contracts.md:203-210` ne mentionne l'impact que côté FRONT-2 (ajout d'un champ),
pas côté état persisté. À trancher avec BACK-4, dans la même livraison que l'élargissement.

### [à surveiller] BACK-2 peut exposer l'adresse e-mail Figma là où BACK-1 la retire explicitement

`lib/figma-connection.ts:164` : `readableString(body["handle"]) ?? readableString(body["email"])`
— si `handle` est absent, `account.accountName` devient l'adresse e-mail du compte. Cette
valeur est persistée par BACK-4 et affichée par FRONT-12 dans le résumé du bloc replié.

`lib/jira-connection.ts:58-60` (invariant 4) tranche l'inverse sur la même donnée : « ce
corps peut contenir l'adresse e-mail du compte […] Seul `displayName` […] ressort ». Deux
positions opposées sur la même classe de donnée, dans la même livraison. En choisir une.

### [mineur] Duplication entre les trois fichiers

Signalé sans demande de refactor : regex de jeton transportable en en-tête
(`jira:239` / `figma:92`, identique), lecture bornée de `Retry-After` avec les mêmes bornes
1–3600 s (`jira:398` / `figma:189`), détection de timeout par nom d'erreur
(`figma:137` / `ai:147`), constante de délai `10_000` déclarée trois fois. Un module commun
existe implicitement ; le créer relève d'un ticket dédié, pas de cette livraison.

### [mineur] BACK-1 : commentaire resté à l'ère `Bearer`

`lib/jira-connection.ts:63`, invariant 6 : « un `Bearer` sur `http://` voyage en clair sur
le réseau ». Le fond reste vrai (`base64(email:jeton)` est réversible), la formulation ne
l'est plus. Vérifié par ailleurs : les quatre occurrences de « Bearer » du fichier sont
toutes dans des commentaires de trace, **aucun message rendu à l'utilisateur ne cite
l'ancien mode**.

### [mineur] BACK-3 : commentaire faux sur les redirections

`lib/ai-connection.ts:208-215` annonce qu'une redirection est « traitée comme telle plus
bas ». Il n'y a aucun traitement plus bas : `redirect: "error"` fait rejeter le `fetch`, et
le cas sort par le `catch` en « impossible de joindre le provider ; […] Vérifiez votre
connexion réseau » (sonde). Commentaire à corriger, et message discutable pour un cas qui
n'est pas un problème de réseau.

### [mineur] BACK-1 et BACK-2 ne libèrent pas le corps sur les branches d'erreur

`jira-connection.ts:493-548` (401, 403, 404, 429, 5xx, 3xx) et `figma-connection.ts:323-338`
retournent sans consommer ni annuler le corps. `ai-connection.ts:160-167` fait l'inverse et
documente pourquoi. Aucun impact fonctionnel observé ; connexion gardée jusqu'au GC côté
undici.

### [mineur] BACK-1 dépend de `Buffer` (Node), là où BACK-2 évite les API dépendantes du runtime

`jira-connection.ts:283`. `figma-connection.ts:133-135` prend soin de ne pas supposer
`DOMException` « selon le runtime (Node / Edge) » ; BACK-1 fige Node. Vérifié en revanche
par sonde locale que `redirect: "manual"` renvoie bien le vrai `302` et son en-tête
`location` sous Node 26 — la branche 3xx de BACK-1 fonctionne dans le runtime visé.

## Non couvert

- **Aucun chemin de succès réel.** Aucun jeton Jira, Figma ou IA valide n'existe dans cet
  environnement : toutes les branches `200` n'ont été exercées que par `fetch` stubé. La
  forme réelle des corps de `/rest/api/3/myself` et `/v1/me` reste une lecture de
  documentation, comme les fichiers le disent eux-mêmes.
- **Aucune sonde réseau refaite.** Les codes HTTP cités dans les en-têtes des trois fichiers
  (401/403/404 sur `ecosystem.atlassian.net`, `api.figma.com`) n'ont pas été re-sondés ;
  seule leur cohérence interne avec le code a été vérifiée.
- **DeepSeek** : `endpointProven: false` reste non levé, et rien dans cet audit ne pouvait le
  lever. L'obligation posée à BACK-3 (confirmer `/models` avec une clé réelle) reste ouverte.
- **Runtime Edge** non testé : `Buffer`, `redirect: "manual"` et `DOMException` n'ont été
  observés que sous Node 26.7.
- **`lib/providers-api.ts`** relu comme dépendance seulement ; son audit du 04/09/2026 fait
  foi.
- **Pas de test automatisé** exécuté ni écrit : il n'en existe aucun pour `lib/` (dette déjà
  connue), donc aucune non-régression de ces modules n'est outillée pour les livraisons
  suivantes.
