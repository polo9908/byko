## Constats

### 1. [bloquant] Le contournement du garde-fou `Secret` par `toJSON` est toujours ouvert : le masque atteint le disque avec `status: "written"`

`lib/token-storage.ts:379-438` (`findSecretPath`), garantie énoncée en `lib/token-storage.ts:44-47` et `docs/architecture/token-storage.md:233-240`.

**Ce qui se passe.** Le correctif fait dérouler `toJSON()` **en boucle** (`for (;;)`, lignes 397-414) jusqu'à obtenir une valeur sans `toJSON`. Or `JSON.stringify` ne déroule `toJSON` **qu'une seule fois par niveau** (spec, `SerializeJSONProperty`), puis sérialise les **propriétés propres énumérables** de la valeur obtenue — sans rappeler le `toJSON` de celle-ci. Vérifié directement :

```
JSON.stringify({a: {toJSON: () => ({toJSON: () => 42})}})   →   {"a":{}}
```

Le `toJSON` interne n'est jamais appelé. La garde et `JSON.stringify` inspectent donc deux valeurs **différentes**, et la garde peut s'arrêter sur une valeur inoffensive pendant que `JSON.stringify` en sérialise une autre, dangereuse.

**Reproduction** (aucune ruse sur l'argument `key`, identique en ES2017 et ES2022) :

```js
const Y = { apiToken: secret, toJSON: () => "safe" };
const X = { toJSON: () => Y };
await store.write({ jira: X });
```

- `JSON.stringify` : déroule `X.toJSON()` → `Y`, puis sérialise les propriétés propres de `Y` → `{"jira":{"apiToken":"••••lpha"}}`.
- `findSecretPath` : déroule `X.toJSON()` → `Y`, **puis continue** et déroule `Y.toJSON()` → `"safe"`. Aucun `Secret` trouvé.

Résultat obtenu : `status: "written"`, et le clair réellement persisté dans le coffre est `{"jira":{"apiToken":"••••lpha"}}`.

**Variante, même cause** : `findSecretPath` appelle `toJSON()` **sans argument**, alors que `JSON.stringify` lui passe la clé de propriété (`{z: {toJSON: k => "key=" + k}}` → `{"z":"key=z"}`). Un `toJSON(k)` qui dépend de `k` voit donc `undefined` dans la garde et sa vraie clé dans `JSON.stringify`. Même issue : masque persisté, écriture acceptée (échec 5.7 de ma sonde).

**Ce que ça casse pour l'utilisateur.** Identique au constat n°1 de la 1re passe, non résolu : le coffre enregistre `••••lpha` à la place du jeton. La sauvegarde est annoncée réussie, l'onboarding se termine, et la panne ne se manifeste qu'au test de connexion suivant sous la forme d'un « jeton invalide » incompréhensible — sans aucun moyen de savoir que le jeton saisi n'a jamais été écrit.

**Direction de correction** (une passe) : ne pas boucler. À chaque nœud, dans cet ordre — (1) tester `isSecret` ; (2) si la valeur est un objet portant un `toJSON` appelable, l'appeler **une seule fois**, en lui passant la clé de propriété courante (`""` à la racine, le nom de la propriété, l'index sous forme de chaîne dans un tableau) ; (3) retester `isSecret` sur le résultat ; (4) récurser sur les propriétés propres énumérables du résultat **sans jamais rappeler son `toJSON`**. C'est exactement le parcours de `SerializeJSONProperty`. Le `WeakSet` anti-cycle ne doit alors plus servir qu'à la récursion.

### 2. [bloquant] La même boucle ne termine pas sur certaines entrées : le processus Node se fige définitivement

`lib/token-storage.ts:397-414`.

**Ce qui se passe.** La boucle `for (;;)` ne sort que si `toJSON()` finit par rendre une valeur sans `toJSON`, ou une valeur **déjà présente dans le `WeakSet`**. Un `toJSON` qui rend à chaque appel un **objet neuf** portant lui-même un `toJSON` n'est jamais retenu par le `WeakSet` : la boucle tourne indéfiniment. Elle est **synchrone**, donc elle bloque la boucle d'événements Node entière.

**Reproduction** :

```js
function fresh() { return { toJSON: () => fresh() }; }
encryptDocument(key, { jira: fresh() });
```

`JSON.stringify` du même document termine instantanément et rend `{"jira":{}}` — donc aucun danger réel, la garde se fige sur une entrée que `JSON.stringify` traite sans broncher. `encryptDocument` n'est jamais revenu : processus toujours vivant après **25 s**, tué par la sonde (SIGKILL). Aucune OOM, la mémoire est récupérée par le GC — c'est une boucle CPU pure, elle ne s'arrêtera jamais d'elle-même.

**Ce que ça casse pour l'utilisateur.** Le serveur ne répond plus à *aucune* requête — pas seulement à la sauvegarde en cours. Il faut le tuer. Et c'est précisément le défaut que le correctif n°3 de cette même livraison prétend fermer : le délai de 30 s d'`UPDATE_MUTATE_TIMEOUT_MS` ne borne que `mutate`, pas `encryptDocument` — et de toute façon aucun `setTimeout` ne peut interrompre une boucle synchrone. Ce constat naît du correctif audité : il se corrige avant le commit, il n'ouvre pas de ticket.

La correction du constat n°1 (un seul déroulement, jamais de boucle) supprime celui-ci par construction.

### 3. [mineur] La même boucle refuse des écritures parfaitement légitimes

`lib/token-storage.ts:397-414`. Symétrique du constat n°1, dans l'autre sens :

```js
encryptDocument(key, { a: { toJSON: () => ({ toJSON: () => secret }) } });
```

`JSON.stringify` rend `{"a":{}}` : le `Secret` n'atteint jamais le disque, l'écriture est sans danger. La garde, elle, déroule deux fois, trouve le `Secret` et refuse avec `invalid_payload` en désignant le chemin `a`. Faux positif : une sauvegarde échoue et le message d'erreur accuse à tort la présence d'un `Secret` non déballé. Le sens de l'échec est prudent (on refuse au lieu d'écrire faux), d'où la sévérité mineure — mais c'est la même cause racine que les constats n°1 et n°2 et la même correction l'élimine.

### 4. [mineur] Le code et la documentation affirment tous deux suivre `JSON.stringify`, ce qui est faux

`lib/token-storage.ts:391-392` : « On rejoue donc ici la même résolution que `JSON.stringify` […] niveau par niveau ». `docs/architecture/token-storage.md:237` : « Cette détection suit `JSON.stringify` jusqu'au bout ».

Les deux énoncés sont démentis par les constats n°1 à n°3 : le déroulement en boucle n'est pas ce que fait `JSON.stringify`, et l'argument `key` n'est pas transmis. C'est le même défaut de forme que celui relevé en sévérité bloquante sur ARCHI-2 le 29/08/2026 — une garantie énoncée en absolu et non tenue — et le document se donne lui-même la règle (`ligne 7` : « en cas d'écart entre ce fichier et le code, c'est le code qui fait foi »). À reprendre en même temps que le code : une fois la correction du n°1 faite, l'affirmation redeviendra vraie et il n'y aura qu'à s'assurer qu'elle mentionne le déroulement **unique** et le passage de la clé.

`package.json` n'expose que `dev`, `build`, `start`, `lint`. Aucun test dans le dépôt, sur le module le plus sensible du projet.

Ce n'est plus une remarque de principe. Quatre sondes indépendantes se sont succédé sur ARCHI-3 le 04/09/2026, chacune trouvant ce que la précédente avait manqué : implémentation (83/83), revue croisée (2 défauts), audit QA 1re passe (2 défauts + la file bloquée), et cette 2e passe (le correctif du défaut principal est incomplet et introduit une boucle infinie). ### 6. [mineur] Le `fsync` de `master.key` est posé, mais aucun des deux chemins d'écriture ne synchronise le **répertoire**

`lib/token-storage.ts:706-717` (clé) et `lib/token-storage.ts:748-769` (coffre).

Le point d'arbitrage de la 1re passe est traité : la clé est désormais ouverte, écrite, `sync()`ée puis fermée, symétriquement au coffre. Je le considère clos.

Reste, sur les deux chemins, qu'aucun `fsync` n'est fait sur le **répertoire** `~/.bcc` après la création de la clé et après le `rename` du coffre. Sur POSIX, `fsync` d'un fichier ne garantit pas la persistance de son entrée de répertoire : après coupure d'alimentation, le fichier synchronisé peut ne pas apparaître, ou l'ancien coffre réapparaître. La fenêtre est étroite et le scénario (coupure d'alimentation franche) est hors du modèle de menace documenté. Je le note pour mémoire, sans en faire une demande de correction ni un ticket : c'est de la dette, symétrique sur les deux chemins, et la doc (§Écriture atomique) ne promet pas explicitement la durabilité de l'entrée de répertoire.

## Non couvert

- **Les tests du périmètre n'ont pas pu être exécutés** : il n'en existe aucun (constat n°5). Ce que je rapporte vient exclusivement de ma sonde jetable, elle-même non reproductible — ce rapport a le défaut qu'il dénonce.
- **L'audit console n'a rien pu observer sur ce périmètre.** Le serveur a bien démarré et servi `GET / 200` sans avertissement, mais aucun fichier applicatif n'importe `lib/token-storage.ts` ni `lib/secret.ts`, et `app/api/` n'existe pas. Ces deux modules n'ont **aucune surface d'exécution** aujourd'hui : leur premier vrai test d'intégration sera BACK-4, et les constats n°1 et n°2 ne se manifesteront qu'à ce moment-là.
- **Je n'ai pas exploré exhaustivement les divergences entre `findSecretPath` et `JSON.stringify`.** J'en ai trouvé quatre (déroulement en boucle, argument `key` non transmis, faux positif, non-terminaison) en ciblant la sémantique de `toJSON`. Il peut en rester : `replacer`, propriétés symboliques, `Proxy` avec piège `get` sur `toJSON`, objets à prototype `null`, `BigInt`, getters qui changent de valeur entre deux lectures. Tant que la garde ne réplique pas littéralement `SerializeJSONProperty`, cette famille de contournements n'est pas fermée — c'est un argument de plus pour la correction proposée au constat n°1 plutôt qu'un rustinage cas par cas.
- **Concurrence inter-processus non testée** : `update()` ne sérialise qu'à l'intérieur d'un processus, la doc l'assume (§Limites connues). Je n'ai pas rejoué deux processus Node écrivant simultanément.
- **Résistance cryptographique non évaluée.** J'ai vérifié le bon usage d'AES-256-GCM (AAD, IV non déterministe, tag de 16 octets, rejet des altérations), pas la primitive elle-même.
- **Le `fsync` n'a pas été vérifié par une coupure réelle** : j'ai relu l'appel à `handle.sync()`, je n'ai pas provoqué de perte d'alimentation.
