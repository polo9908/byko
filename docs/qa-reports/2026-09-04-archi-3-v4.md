## Verdict

Ce que cette passe établit, par sonde indépendante :

- le bloquant de la 3e passe (valeurs appelables) est **fermé** : 12 formes de fonctions /
  Proxy porteurs d'un `toJSON` sont toutes détectées, à la racine, en profondeur et en
  tableau ;
- les deux contre-exemples de la 2e passe sont **non régressés** ;
- sur **6000 documents aléatoires** mêlant `toJSON`, fonctions augmentées, Proxy, tableaux
  et `Secret` placés au hasard : **zéro fuite**, zéro exception non rattrapée ;
- sur 8 documents bénins, le clair écrit est **octet pour octet** celui de
  `JSON.stringify` — la garde ne dérive plus du sérialiseur, ni en détection ni en faux
  positif ;
- 7 formes pathologiques de terminaison (cycle via `toJSON` vers un ancêtre,
  `toJSON` renvoyant `this`, `toJSON`/fonction récursifs à l'infini, Proxy révoqué en cours
  d'inspection) terminent toutes en moins de 2 ms, en `invalid_payload` ou en document
  fidèle.

**Sur la requalification demandée (double appel `toJSON`) : non, ce point ne doit pas être
classé bloquant.** Justification et réserve au constat 1.

## Constats

### [à surveiller] L'invariant documenté ne couvre que `toJSON` ; les accesseurs et les pièges de `Proxy` divergent exactement pareil

`lib/token-storage.ts:525-530` (commentaire INVARIANT) et
`docs/architecture/token-storage.md:320` (ligne du tableau §Limites connues), ainsi que
`docs/architecture/token-storage.md:503-513`.

Les deux textes énoncent l'invariant sur les seuls `toJSON` : « ses `toJSON`, s'il en
fournit, doivent être PURS », « Les `toJSON` d'`encode()` doivent être purs ». Or la cause
n'est pas `toJSON` : c'est le **double parcours** du document (`findSecretPath` puis
`JSON.stringify`), qui réexécute *tout* ce que le graphe contient de code — `toJSON`, mais
aussi les accesseurs (`get`) et les pièges de `Proxy`. Le module le sait d'ailleurs déjà
ailleurs (`lib/token-storage.ts:504-508` : « Parcourir le document exécute ses accesseurs
(`get`) et ses pièges de Proxy »).

Trois cas reproduits, tous les trois écrivant un coffre valide contenant
`{"…":{"apiToken":"••••y7z6"}}` — le masque à la place du jeton :

| Cas | Document | Couvert par l'invariant tel qu'écrit ? |
| --- | --- | --- |
| 41 | `{ o: { toJSON: () => (++n === 1 ? { safe: true } : { apiToken: secret }) } }` | oui |
| 42 | `{ o: <objet avec un getter `apiToken` renvoyant `"safe"` au 1er accès, `secret` au 2e> }` | **non** — aucun `toJSON` dans le document |
| 43 | `{ p: new Proxy({ apiToken: "safe" }, { get: … 1er appel `"safe"`, 2e `secret` }) }` | **non** — aucun `toJSON` dans le document |

Reproduction : appeler `encryptDocument(clé, doc)` sur l'un des trois, puis
`decryptDocument` sur le retour — le clair contient le masque. Identique en ES2017 et
ES2022.

Ce que ça casse pour l'utilisateur : rien aujourd'hui (aucun code du dépôt n'importe ces
modules ; `app/api/` n'existe pas). Le jour où BACK-4 écrirait un `encode()` non
déterministe, le coffre serait écrit valide avec le masque, et la panne se manifesterait au
test de connexion suivant par un « jeton invalide » incompréhensible.

**Pourquoi ce n'est pas bloquant**, réponse explicite à la question posée :

1. la conséquence est une **corruption fonctionnelle**, pas une divulgation : ce qui est
   écrit est le masque, une valeur conçue pour être non sensible. Aucun jeton ne sort ;
2. le déclencheur est du **code applicatif impur**, jamais du contenu utilisateur : la
   structure du document vient d'`encode()` (BACK-4) ; une chaîne saisie par l'utilisateur
   ne peut pas devenir un accesseur ni un piège de Proxy. Il n'existe aujourd'hui aucun
   appelant, donc aucun chemin d'exécution atteignable ;
3. la fermeture complète suppose de fusionner les deux parcours (inspection depuis un
   `replacer` de `JSON.stringify`) : une réécriture plus large, sur un module qui vient
   d'enchaîner trois régressions sur ce même code. La sonde de cette passe montre que la
   version actuelle est fidèle partout ailleurs — c'est un capital à ne pas remettre en jeu
   sous pression.

**Ce qu'il faut corriger avant le commit** (rédaction seule, pas de code) : dans les deux
endroits cités, remplacer « ses `toJSON` doivent être purs » par la formulation qui couvre
réellement le risque, du type « les `toJSON`, **les accesseurs (`get`) et les pièges de
`Proxy`** du document rendu par `encode()` doivent être purs : ils sont évalués deux fois,
une fois par la garde et une fois par `JSON.stringify` ». Sans cela, un BACK-4 qui n'écrit
aucun `toJSON` conclura à juste titre que l'invariant ne le concerne pas, alors que deux des
trois cas ci-dessus ne contiennent aucun `toJSON`.

Constat né de la livraison auditée (l'invariant a été rédigé dans cette livraison) : pas de
ticket, correction dans la même livraison.
