## Constats

### [bloquant] Un POST au jeton invalide écrase et détruit une connexion Jira/Figma/IA valide

`lib/settings-service.ts:48-63` (`saveJira`, motif identique dans `saveFigma`/`saveAi`) :
`nextJira` est reconstruit intégralement à partir du seul verdict du test rejoué, sans jamais
regarder l'état actuellement `connected` du bloc. Vérifié à l'exécution (sonde jetable,
supprimée après vérification, aucun fichier resté dans le dépôt) :

1. `POST /api/settings` avec un jeton Jira valide → `{"status":"connected", ...}`.
2. `POST /api/settings` sur le **même bloc** avec un jeton invalide (401 simulé) →
   réponse `{"block":"jira","status":"error", ...}`, **et** l'état persisté passe de
   `connected` à `not_connected` avec `lastError`. Le `Secret` du jeton précédemment valide
   est perdu : `store.read()` ne le retrouve plus, aucune récupération possible.

Conséquence utilisateur : un test au blur qui échoue temporairement (faute de frappe en
cours d'édition d'un autre champ du même bloc, jeton régénéré entre-temps côté provider,
incident réseau) détruit silencieusement une connexion qui fonctionnait, alors que l'US du
ticket est explicitement « ne pas avoir à ressaisir mes jetons si je quitte le wizard et
reviens plus tard ». Le contrat (`PersistedConnectionError` n'existant que sur
`not_connected`) rend cette forme représentable, mais aucun ticket ni arbitrage ne demande de
dégrader une connexion déjà validée sur un nouvel échec de test. Traité comme un défaut de
cette livraison (né du correctif audité), pas comme de la dette pré-existante — n'ouvre donc
pas de ticket séparé, à corriger avant le commit de BACK-4 (par ex. ne dégrader que si le
bloc n'était pas déjà `connected`, ou conserver l'ancien `Secret` avec le nouveau
`lastError` — au choix de l'implémentation, mais pas l'écrasement actuel).

### [à surveiller] `readOptionalError` accepte n'importe quelle chaîne comme `code`

`lib/settings-store.ts:186-191` : `value.code as TCode` caste sans vérifier l'appartenance de
`value.code` à l'union de codes déclarée pour le bloc (`JiraTestConnectionErrorCode`, etc.).
Vérifié à l'exécution : `decodeSettingsDocument({..., jira: { status: "not_connected",
lastError: { message: "x", code: "n-importe-quoi-pas-dans-la-liste" } }, ...})` rend
`{ ok: true, value: { ..., code: "n-importe-quoi-pas-dans-la-liste" } }` — accepté tel quel,
et ce `code` non conforme au contrat ressortirait sur `GET /api/settings`. Portée réelle
limitée aujourd'hui : le seul chemin d'écriture actuel (`settings-service.ts`) ne pose que des
`code` déjà typés par les connecteurs BACK-1/2/3 ; le trou n'est exploitable qu'en cas de
coffre modifié hors de l'application (nécessite déjà la clé et le fichier chiffré) ou d'une
version future du schéma qui introduirait de nouveaux codes. Né de cette livraison — pas de
ticket, à corriger avant commit (valider `code` contre une liste explicite, comme le fait déjà
`isProviderId` pour `provider`).

### [à surveiller] Aucun test n'exerce le vrai handler `app/api/settings/route.ts`

`test/settings-service.test.ts:57-69` (fonction `readSettings`) réimplémente localement la
branche `absent`/`error`/`success` de `GET`, au lieu d'appeler la fonction `GET` exportée par
`app/api/settings/route.ts`. Le fichier n'est importé par aucun test. Vérifié en injectant,
sur une copie hors dépôt, une régression directement dans `route.ts` (conflation de
`result.status === "error"` avec `result.status === "absent"`, exactement le défaut que le
critère d'acceptation du ticket interdit) : `pnpm run test` reste vert, 118/118 pass — la
suite ne l'aurait pas vu passer en production. L'en-tête du fichier de test affirme que « toute
la logique testée ici emprunte … exactement le chemin d'une requête réelle » : vrai pour les
fonctions de `lib/` appelées, faux pour le branchement HTTP lui-même de `route.ts`, jamais
exécuté par la suite. Né de cette livraison — pas de ticket, à corriger avant commit (appeler
`GET`/`POST` de `route.ts` avec une `Request` construite, ou a minima reformuler le commentaire
pour ne pas affirmer une couverture qui n'existe pas).

### [mineur] `dynamic = "force-dynamic"` justifié par une affirmation non vérifiée

`app/api/settings/route.ts:10-11,22` : le commentaire « Jamais mis en cache : la
configuration change à chaque sauvegarde… » présente `force-dynamic` comme nécessaire à cette
garantie. Vérifié dans `node_modules/next/dist/docs/01-app/01-getting-started/
15-route-handlers.md` (Next 16.3.3, version installée) : « Route Handlers are not cached by
default. You can, however, opt into caching for `GET` methods… » — c'est `force-static` qui
activerait un cache, pas l'absence de `force-dynamic`. Le comportement obtenu (jamais mis en
cache) est correct, mais le commentaire affirme une nécessité qui n'existe pas dans cette
version, ce que la règle du projet contre les affirmations non vérifiées interdit. Aucun
impact fonctionnel — le `export const dynamic` est inoffensif, juste inutile et mal justifié.

### [à surveiller — pré-existant, ticket ouvert] Avertissement Turbopack sur `lib/token-storage.ts`

`pnpm run build` (Turbopack) émet : « Warning: Dynamic filesystem access causes tracing of the
whole project » sur `lib/token-storage.ts:891` (`readFile(location.configPath, "utf8")`),
atteint pour la première fois via `lib/settings-store.ts` → `app/api/settings/route.ts` — ce
code appartient à ARCHI-3 et n'est pas modifié par BACK-4, mais c'est cette livraison qui
crée la première route à l'exercer et donc la première occasion de voir l'avertissement.
Risque documenté par Next : traçage de tout le projet (y compris `public/`) dans le bundle
serveur, déploiements plus lents ou échec de limite de taille. Ne bloque pas le build
aujourd'hui.
**Ticket non ouvert** : `gh issue create` (et `gh label create`) refusés par le classifieur de
permissions de la session dans cet environnement (deux tentatives, deux refus). À ouvrir
manuellement — titre suggéré : « Avertissement Turbopack : lecture dynamique du FS dans
`lib/token-storage.ts` trace tout le projet », portant sur ARCHI-3.

## Position sur les trois points relevés (§4 de la demande)

1. **Écrasement d'une connexion valide** (`lib/settings-service.ts`) : confirmé à l'exécution,
   inacceptable en l'état — **bloquant**, voir constat ci-dessus.
2. **`readOptionalError` / `code as TCode`** (`lib/settings-store.ts`) : trou réel mais à
   portée limitée aujourd'hui (nécessite un coffre altéré hors application, déjà protégé par
   la clé) — **à surveiller**, à corriger avant commit.
3. **`dynamic = "force-dynamic"`** (`app/api/settings/route.ts`) : la doc Next 16.3.3
   confirme que les Route Handlers ne sont pas mis en cache par défaut ; le commentaire
   affirme une nécessité qui n'existe pas — **mineur**, comportement correct, justification
   fausse à reformuler.
