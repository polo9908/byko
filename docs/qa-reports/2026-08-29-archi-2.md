## Constats

### [bloquant] La « garantie structurelle » de non-exposition des jetons est fausse : un chemin de fuite compile

`lib/types/settings.ts:7-10` et `docs/api-contracts.md:25-30` affirment que les jetons ne
peuvent pas atteindre une réponse et qu'« exposer un jeton exigerait de modifier ce
contrat : ce n'est pas un oubli possible dans une implémentation ».

C'est faux : les types TypeScript ne sont pas exacts. Le contrôle de propriétés
excédentaires ne s'applique qu'aux littéraux d'objet frais ; dès que la valeur passe par une
variable ou un spread, `apiToken` voyage à l'exécution sans erreur de compilation.
Reproduction (compilée contre le fichier livré, `tsc --noEmit --strict`, exit 0) :

```ts
function handler(creds: JiraCredentials): TestConnectionResponse {
  const payload = {
    block: "jira" as const,
    status: "success" as const,
    account: { accountName: "paul" },
    ...creds,            // apiToken embarqué
  };
  return payload;        // aucune erreur : exit 0
}
```

S'y ajoute que `NextResponse.json(body)` accepte n'importe quel corps : le type n'est pas
vérifié à la frontière de sérialisation.

Ce qui est correct et vérifié par ailleurs : **aucun type de sortie ne déclare de champ
jeton**, ni directement, ni optionnellement, ni via un type imbriqué. `apiToken` n'existe que
dans `JiraCredentials`, `FigmaCredentials`, `AiCredentials`, référencés uniquement par
`*TestConnectionRequest` et `*SettingsUpdate` — tous des entrées. La chaîne a été remontée
type par type.

Ce que ça casse : BACK-1/2/3/4 lisent ce contrat comme une dispense de contrôle en sortie.
Un handler qui renvoie `{ ...body, status: "success" }` — le raccourci le plus banal — expédie
le jeton au navigateur, sans que lint, `tsc` ni `build` ne bronchent. Dans la zone la plus
sensible du projet, une garantie fausse est pire qu'une garantie absente.

Correction attendue (avant tout démarrage de BACK-1) : requalifier la garantie en « aucun
champ jeton n'est **déclaré** en sortie » et poser explicitement l'obligation, pour BACK-1 à
BACK-4, de construire chaque réponse par projection explicite champ à champ — jamais par
spread ni réutilisation du corps de requête.

### [à surveiller] `SaveSettingsResponse` ne porte pas `block`, contre l'argument que le contrat s'applique à lui-même

`lib/types/settings.ts:338-340` : `{ status: "success" } | { status: "error", message }`.

`docs/api-contracts.md:84-86` et `settings.ts:107-116` justifient l'écho de `block` sur les
réponses de test par la concurrence : le test au blur (règle produit ligne 10) met plusieurs
requêtes en vol, le front doit rattacher chaque réponse à son bloc sans se fier à l'ordre
d'arrivée. `POST /api/settings` est déclenché par le même flux, bloc par bloc — l'argument
vaut à l'identique, la conclusion n'a pas été appliquée. Deux sauvegardes en vol : le front
peut afficher l'erreur de Figma sur le bloc Jira.

### [à surveiller] `pending` n'a aucun mécanisme de résolution

`lib/types/settings.ts:119-123`. `TestConnectionPending` ne porte ni identifiant de test, ni
`retryAfter`, ni endpoint de suivi. Un front conforme au contrat qui reçoit `pending` reste
en spinner indéfiniment, sans pouvoir distinguer « test en cours » d'« appel perdu ». Aucun
délai d'attente n'est exprimé nulle part dans le contrat.

`docs/api-contracts.md:164-171` identifie ce point et l'ouvre à arbitrage (retirer `pending`
ou compléter l'asynchrone). Le constat reste consigné : il est dans le contrat livré, pas
seulement dans la liste des questions.

### [à surveiller] Aucune convention de code HTTP ni garde de type à l'exécution

`docs/api-contracts.md:191-198` et `204-208`. Le contrat définit l'enveloppe applicative
`status` mais pas le code HTTP, et le fichier étant de types purs, tout consommateur écrira
un `as` à la frontière de parsing. Conséquence directe : un `200 OK` au corps vide, tronqué
ou non conforme sera casté en `GetSettingsResponse` et lu comme `status !== "error"` — donc
traité comme « aucune configuration », qui est précisément la confusion que la variante
d'erreur de `GetSettingsResponse` a été ajoutée pour empêcher. La protection existe dans les
types, elle est contournée à la frontière.

Point positif vérifié : `GetSettingsResponse` distingue bien, au niveau du type, « aucune
configuration » (`success` + trois `not_connected`) d'« impossible de lire la configuration »
(`error` + `message` requis). Et un test en échec ne peut pas être confondu avec un succès :
union discriminée par `block` puis `status`, narrowing vérifié par compilation.

### [à surveiller] Le commentaire de `RequiredConnectionStatus` affirme une correspondance que la compilation ne vérifie pas

`lib/types/settings.ts:232-237` : « C'est le vocabulaire de statut exact de
`JiraSettingsState` et `AiSettingsState` ci-dessous. » Or `JiraSettingsState` (l. 252-254) et
`AiSettingsState` (l. 270-272) écrivent leurs littéraux en dur et ne référencent ni
`RequiredConnectionStatus` ni `ConnectionStatus`. Les deux alias sont exportés et
non référencés (hors `Exclude`). Ajouter demain un statut à `ConnectionStatus` (ex.
`expired`) le propagerait à `RequiredConnectionStatus` sans toucher aux états : le
commentaire devient faux en silence, sans erreur de compilation.

`docs/api-contracts.md:210-218` constate exactement l'inverse du commentaire du code
(« n'est plus référencé par aucun autre type… son commentaire affirme une correspondance que
la compilation ne vérifie plus »). Le commentaire de `settings.ts` n'a pas été mis à jour :
la doc et le code se contredisent sur le même type.

### [mineur] Le champ `code` n'est rattaché à aucune ligne de ticket

`lib/types/settings.ts:143`. Les **neuf valeurs** sont sourcées une à une (`invalid_url`,
`invalid_token`, `instance_unreachable`, `timeout` ← BACK-1 l. 113/119 ; `rate_limited` ←
BACK-2 l. 136/141 ; `quota_exceeded`, `provider_unavailable` ← BACK-3 l. 158). Le **champ**
lui-même n'est pas dans ARCHI-2 l. 49, qui décrit la réponse comme

à `block`. Incohérence interne : `docs/api-contracts.md:118-119` justifie l'absence de `code`
sur `GET /api/settings` par « aucun ticket n'en cite pour ce cas » — critère qui, appliqué à
`test-connection`, aurait exclu `code` aussi. Non affiché à l'utilisateur (`message` est la
seule source d'affichage), donc aucune donnée fausse à l'écran.

### [mineur] `message` requis en erreur : resserrement non listé comme divergence

ARCHI-2 l. 49 écrit `message?: string`. Le contrat le rend obligatoire sur toutes les
variantes d'erreur. Le motif est bon et sourcé (FRONT-3 l. 246), mais la section « Divergence

### [mineur] Aucun champ pour le « nom de l'instance Jira » attendu par FRONT-5

FRONT-5 l. 288 demande d'afficher le « nom de l'instance Jira ». Le contrat expose

`JiraTestConnectionErrorCode` porte `timeout`, pas les deux autres blocs. Fidèle aux tickets

ailleurs `ConnectionStatus` comme « état persisté d'une connexion » alors qu'aucun type

## Constat 1 — [bloquant] Garantie fausse sur les jetons : **LEVÉ**

`lib/types/settings.ts:7-24` et `docs/api-contracts.md:20-52` sont réécrits et **disent
désormais la même chose**.

- La séparation GARANTI / NON GARANTI est exacte. Le « garanti » est requalifié au niveau
  **déclaratif** (« aucun type de SORTIE ne *déclare* de champ jeton ») — vérifié : `apiToken`
  n'apparaît qu'aux lignes 68, 73, 79, dans les trois `*Credentials`, tous en entrée.
- Le chemin de fuite est **explicitement nommé**, avec l'extrait qui compile
  (`{ …, ...credentials }`) et la mention que `NextResponse.json` ne vérifie pas le corps.
  Sonde de compilation : ce chemin compile toujours (exit 0) — la doc décrit donc un fait,

- L'obligation faite à BACK-1/2/3/4 est posée sans ambiguïté : construire chaque réponse

Aucune affirmation de garantie non tenue ne subsiste **dans la zone jetons**. Deux

## Nouveaux constats de la contre-vérification

### [mineur] Une garantie de compilation reste énoncée en absolu et ne tient pas

`docs/api-contracts.md:115` (« Envoyer des credentials d'un bloc sous le `block` d'un autre
ne compile pas ») et `lib/types/settings.ts:112-114`.

Vrai dans un sens, faux dans l'autre. Sonde compilée :

```ts
const jira: JiraCredentials = { instanceUrl: "…", apiToken: "…" };
const body = { block: "figma" as const, credentials: jira };
const req: TestConnectionRequest = body;   // tsc exit 0
```

Des credentials Jira passent sous `block: "figma"` dès qu'ils transitent par une variable —
même mécanisme d'excess property check que celui décrit au §Jetons. L'exemple inverse cité
en commentaire (credentials Figma sous `block: "jira"`) échoue bien, lui, parce que
`instanceUrl` manque.

Portée limitée : c'est une **requête**, où les jetons ont le droit d'être ; aucune donnée
fausse à l'écran. Correction attendue : aligner la formulation sur celle du §Jetons
(« l'oubli d'un champ requis ne compile pas ; un champ excédentaire passé par variable, si »).

### [mineur] Bandeau de section réaffirmant un absolu que l'en-tête vient de qualifier

`lib/types/settings.ts:62` : « Credentials (entrées uniquement — jamais renvoyés par une
réponse) ». Un lecteur qui n'ouvre le fichier qu'à cette section retrouve exactement la
formulation que l'en-tête a corrigée 40 lignes plus haut. Aucune conséquence technique.
