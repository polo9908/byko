## Constats

### [à surveiller] `DOMAIN_LIKE` rejette tout hôte avec un port explicite

`lib/jira-connection.ts:377`. Le groupe `(:\d+)?` est placé **avant** le groupe des labels
pointés `(\.[a-z0-9]…)+`, qui exige au moins une occurrence. Un port ne peut donc être
accepté que s'il est suivi d'un point — position qui n'existe dans aucun hôte réel.

Reproduction (`new URL(u).host` passé à `DOMAIN_LIKE.test`) :

| Saisie | `host` | Cité ? |
| --- | --- | --- |
| `https://mon-entreprise.atlassian.net` | `mon-entreprise.atlassian.net` | oui |
| `https://jira.corp-interne.example.com` | `jira.corp-interne.example.com` | oui |
| `https://192.168.1.10` | `192.168.1.10` | oui |
| `https://jira.entreprise.com:8443` | `jira.entreprise.com:8443` | **non** |
| `https://192.168.1.10:8080` | `192.168.1.10:8080` | **non** |
| `https://localhost` / `https://localhost:8080` | `localhost` / `localhost:8080` | non (attendu : pas de point) |
| `https://[::1]:8443` | `[::1]:8443` | non |
| `foo:8080.com` | — | **oui** (le seul cas où le groupe port sert) |

Ce que ça casse : une instance Jira Data Center servie sur un port explicite — la forme la
plus courante d'un déploiement interne — perd son nom d'hôte dans les dix messages de
`describeNetworkFailure` et des branches 401/403/404/429/5xx/3xx. L'utilisateur lit
« Impossible de joindre l'adresse saisie » au lieu de l'adresse, et ne peut plus vérifier
que l'URL testée est bien celle qu'il croit avoir saisie. Aucune donnée fausse, mais le
diagnostic que le fichier construit soigneusement est perdu sur ce cas.

Correction : déplacer `(:\d+)?` après le groupe des labels pointés, en fin d'expression.

### [à surveiller] La garde de type ne couvre pas `credentials` absent — la JSDoc promet toujours l'inverse

`lib/ai-connection.ts:209-216` et `lib/jira-connection.ts:467-475` testent les *champs* de
`credentials`, mais déréférencent `credentials` sans garde. Sondes :

| Appel | Résultat |
| --- | --- |
| `testAiConnection({ provider: "mistral", apiToken: "x" })` | erreur propre ✔ |
| `testAiConnection({ provider: "openai" })` | erreur propre ✔ |
| `testJiraConnection({ email, apiToken })` / `({ instanceUrl, apiToken })` | erreur propre ✔ |
| `testAiConnection(undefined)` | `TypeError: Cannot read properties of undefined (reading 'apiToken')` |
| `testAiConnection(null)` | `TypeError: … (reading 'apiToken')` |
| `testJiraConnection(undefined)` | `TypeError: … (reading 'instanceUrl')` |
| `testFigmaConnection(undefined)` | erreur propre ✔ (`credentials?.apiToken`) |

Ce n'est pas un cas théorique : un `POST /api/settings/test-connection` de corps
`{"block":"jira"}` produit exactement `credentials === undefined`. Or `jira-connection.ts:445`
écrit toujours « Ne lève jamais : tout échec — **y compris une entrée aberrante** — ressort
en `{ status: "error", message }` », et `ai-connection.ts:199` « Ne lève jamais ». L'auteur
de la route lira ces phrases et n'écrira pas de `try/catch` : le `500` nu que le critère
d'acceptation de BACK-1 interdit reste atteignable. `figma-connection.ts:281` montre la
forme correcte en une ligne.

### [à surveiller] Le commentaire qui justifie le correctif du bloquant affirme une valeur non sondée

`lib/ai-connection.ts:94-96` : « les six routes de la table (`lib/providers-api.ts`)
répondent toutes en JSON ». Aucune sonde n'accompagne cette phrase, contrairement à la
règle tenue partout ailleurs dans ces fichiers — et la sonde réseau faite pour cet audit la
contredit partiellement :

```
GET https://api.anthropic.com/v1/models                  → 401  content-type: application/json
GET https://api.openai.com/v1/models                     → 401  content-type: application/json
GET https://api.moonshot.ai/v1/models                    → 401  content-type: application/json; charset=utf-8
GET https://api.x.ai/v1/models                           → 401  content-type: application/json
GET https://generativelanguage.googleapis.com/v1beta/models → 403  content-type: application/json; charset=UTF-8
GET https://api.deepseek.com/models                      → 401  content-type: ABSENT (content-length: 31, server: elb)
```

DeepSeek n'émet **aucun** `content-type` sur son 401. Le 401 est classé avant le contrôle
(`invalidKeyStatuses`), donc rien ne casse aujourd'hui ; mais c'est la preuve que cette
passerelle omet l'en-tête sur au moins une de ses réponses, et DeepSeek est précisément le
provider dont le chemin n'est pas prouvé (`endpointProven: false`). Si son `200` l'omet
aussi, une clé DeepSeek **valide** ressortira en « réponse du provider inexploitable » —
un faux négatif introduit par le correctif. Non prouvable ici : aucune clé réelle. Ne pas
bloquer dessus, mais remplacer la phrase par ce qui est réellement observé, et ajouter
DeepSeek à la liste « à confirmer au premier test avec une clé réelle » déjà présente dans
le fichier.

### [mineur] Le libellé de repli de `citableHost` casse la phrase la plus fréquente

`jira-connection.ts:380` rend `"l'adresse saisie"`, inséré tel quel dans
`jira-connection.ts:394` : « Le domaine **l'adresse saisie** est introuvable. » Les neuf
autres messages restent lisibles. Un libellé sans article (`"cette adresse"`) ou une
formulation dédiée pour la branche `ENOTFOUND` suffirait.

### [mineur] Résiduel assumé : `200` + `content-type: application/json` + corps vide reste un succès

Sonde : `new Response(null, { status: 200, headers: { "content-type": "application/json" } })`
→ `{"block":"ai","status":"success"}`. Conséquence directe du choix — documenté et
légitime — de ne jamais lire le corps chez BACK-3. Le cas exige désormais qu'un
intermédiaire forge un `content-type` JSON, ce qui réduit fortement la portée par rapport à
la 1ʳᵉ passe. Consigné pour mémoire, aucune action demandée.

### [mineur] Les cinq mineurs de la 1ʳᵉ passe sont inchangés

Duplication entre les trois fichiers, commentaire « ère `Bearer` » (`jira:66`), commentaire
faux sur les redirections (`ai:240-249`), corps non libéré sur les branches d'erreur de
BACK-1/2, dépendance à `Buffer` (`jira:287`). Volontairement laissés en l'état, relus et
toujours exacts.

  la documentation, jamais d'une observation.

  observés sous Node 26.7 seulement.
- **Console navigateur** : rien à observer, aucun de ces modules n'est importé par une route
