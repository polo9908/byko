# Audit — ARCHI-3, stockage local chiffré des jetons (3e passe)

04/09/2026 · Agent audité : orchestrateur (3e réécriture de `findSecretPath`) · Portée :
`lib/token-storage.ts`, `lib/secret.ts`, `docs/architecture/token-storage.md` relus en
entier dans leur état actuel (les trois toujours untracked ; rien d'autre modifié depuis
`860a48a`).

## Verdict

**BLOQUANT.**

Les deux contre-exemples de la 2e passe sont **corrigés** : vérifiés, ils passent. Sur
4000 documents aléatoires *sans valeur appelable*, la garde est fidèle à `JSON.stringify`
à 100 % (détection, absence de faux positif, et exactitude du chemin signalé).

Mais la réécriture reste infidèle sur une **troisième** forme, du même défaut de fond :
`resolveJSONValue` n'applique pas `toJSON` aux valeurs **appelables**, alors que
`JSON.stringify` le fait (ECMA-262 §25.5.2.1 étape 2 : « If value is an Object » — une
fonction *est* un Object). Un `Secret` caché derrière le `toJSON` d'une fonction franchit
la garde et son masque est écrit dans le coffre. 889 documents sur 4000 fuient dès que le
générateur aléatoire inclut cette forme.

## Constats

### [bloquant] `resolveJSONValue` n'applique pas `toJSON` aux valeurs appelables : un `Secret` s'échappe et son masque est écrit

`lib/token-storage.ts:400-411` (`resolveJSONValue`), garde d'entrée :

```ts
if (
  (typeof value === "object" && value !== null) ||
  typeof value === "bigint"
) {
```

`typeof value === "function"` manque. `JSON.stringify`, lui, résout bien le `toJSON` d'une
fonction — vérifié sur Node v26.7.0 :

```
JSON.stringify({ a: Object.assign(() => {}, { toJSON: () => ({ apiToken: "X" }) }) })
→ {"a":{"apiToken":"X"}}
```

**Reproduction** (`encryptDocument` appelé directement, ou `store.write()`) :

```ts
const fn = () => {};
fn.toJSON = () => ({ apiToken: secret });   // secret = createSecret("ATATT-…-XYZ9")
encryptDocument(key, { jira: fn });
// attendu  : erreur invalid_payload nommant jira.apiToken
// observé  : status "ok" — le coffre est écrit et contient {"jira":{"apiToken":"••••XYZ9"}}
```

Trois variantes reproduites, toutes acceptées à tort :

- `{ jira: fn }` où `fn.toJSON` renvoie un objet portant le `Secret` (cas ci-dessus) ;
- un **Proxy appelable** dont le piège `get` fournit `toJSON` (`{ figma: proxy }`) ;
- la même fonction **à la racine** : `encryptDocument(key, fn)`.

Une quatrième variante, `fn.toJSON = () => secret` (le `Secret` renvoyé directement),
n'écrit pas le masque mais `{}` — `JSON.stringify` ne rappelle pas `toJSON` sur son retour.
Le jeton est perdu tout autant, sans que rien ne le signale.

**Mesure différentielle**, oracle = `JSON.stringify` réellement exécuté, 4000 documents
aléatoires portant chacun un `Secret` à une position tirée au sort :

| Générateur | Secrets sérialisés non détectés | Faux positifs | Chemin signalé erroné |
| --- | --- | --- | --- |
| sans valeur appelable | **0 / 4000** | 0 | 0 |
| avec valeur appelable | **889 / 4000** | 0 | 0 |

Ce qui casse pour l'utilisateur : c'est exactement la panne que la garde existe pour
empêcher, et que l'en-tête du module décrit lui-même (`lib/token-storage.ts:44-47`) — un
coffre valide contenant `••••XYZ9` à la place du jeton. Rien n'échoue à l'écriture ;
la panne ne se manifeste qu'au test de connexion suivant, sous la forme d'un « jeton
invalide » sans rapport apparent avec la sauvegarde.

**Correctif** — une ligne, dans `resolveJSONValue` uniquement :

```ts
if (
  (typeof value === "object" && value !== null) ||
  typeof value === "function" ||
  typeof value === "bigint"
) {
```

Le test qui suit dans `findSecretPath` (`if (typeof value !== "object" || value === null)
return null;`) reste correct tel quel : une fonction sans `toJSON` continue d'être ignorée,
comme `JSON.stringify` l'omet. J'ai appliqué ce correctif à une **copie hors dépôt** et
rejoué la sonde : **64 OK**, 889 → **0** manqué, 0 faux positif, tous les cas des passes 1
et 2 toujours corrects. Je n'ai touché aucun fichier du dépôt.

**Honnêteté sur l'exploitabilité** : qu'un `encode()` de BACK-4 renvoie une fonction
porteuse d'un `toJSON` est peu vraisemblable. Le classement en bloquant tient à deux
choses, pas à la probabilité du déclencheur : (a) le module *annonce* une fidélité qu'il
n'a pas, et BACK-4 s'y fiera ; (b) c'est le même degré d'exotisme que les deux
contre-exemples déjà jugés bloquants aux passes 1 et 2 — les traiter différemment serait
arbitraire.

### [bloquant] La documentation affirme une fidélité qui n'existe pas

`docs/architecture/token-storage.md:475-482` : « Corrigé en remplaçant la boucle par une
**résolution fidèle à l'algorithme réel** » ; même affirmation dans le commentaire de
`lib/token-storage.ts:380-398` (« Résout `value` **exactement comme**
`SerializeJSONProperty` »). C'est faux sur les valeurs appelables, comme montré ci-dessus.

Sur un module dont la doc est le seul contrat lisible par BACK-4, une garantie écrite qui
ne tient pas est une donnée fausse au sens de la règle de non-invention. À corriger dans la
même passe que le code : soit la fidélité est rétablie (correctif d'une ligne ci-dessus) et
l'affirmation devient vraie, soit la limite est nommée noir sur blanc. La première option
est la bonne. La sous-section « Deuxième défaut sur `toJSON` » devra alors mentionner ce
troisième cas, sans quoi le prochain relecteur croira le sujet clos deux fois alors qu'il
l'a été trois.

### [à surveiller] `toJSON` est invoqué deux fois : la garde et `JSON.stringify` peuvent voir deux graphes différents

`lib/token-storage.ts:502` puis `:518` — `findSecretPath` parcourt le document (et appelle
tous ses `toJSON`), puis `JSON.stringify` le reparcourt et les rappelle. Un `toJSON` non
déterministe montre donc un graphe propre à la garde et un `Secret` au sérialiseur.
Reproduit :

```ts
let n = 0;
const doc = { jira: { toJSON: () => (++n === 1 ? { apiToken: "propre" } : { apiToken: secret }) } };
encryptDocument(key, doc);
// toJSON appelé 2 fois · status "ok" · contenu réellement chiffré : {"jira":{"apiToken":"••••7777"}}
```

Inhérent au principe « inspecter puis sérialiser » ; le fermer vraiment demanderait de
sérialiser une seule fois et d'inspecter le résultat, ou de figer le document avant les
deux passes. **Ce constat naît de la livraison auditée, pas d'une dette antérieure : il
n'ouvre donc pas de ticket** — il se tranche avant le commit, soit par un correctif, soit
par une ligne explicite au §Limites connues qui nomme la contrainte « `encode()` doit
rendre un document dont les `toJSON` sont purs ». Ne pas le laisser implicite.

### [mineur] Un `Secret` sous la clé vide est signalé « (racine) »

`lib/token-storage.ts:434-435` et `:466` — pour `{ "": secret }`, le chemin rendu est
`(racine)` alors que le `Secret` est sur la propriété de nom vide : `path === ""` sert à la
fois de marqueur de racine et de chemin légitime. L'écriture est bien refusée ; seul le
message désigne le mauvais endroit. Vérifié.

### [mineur] Message trompeur sur un dépassement de pile

`lib/token-storage.ts:503-507` — une chaîne de `toJSON` infiniment profonde
(`const mk = () => ({ x: { toJSON: () => mk() } })`) fait déborder la pile ; le `catch`
rend « un accesseur de l'objet a levé une exception », ce qui n'est pas ce qui s'est passé.
Le comportement est correct (refus, aucune écriture, `JSON.stringify` natif lève un
`RangeError` sur le même document) ; c'est le diagnostic qui égare.

## Ce qui a été confirmé correct

Rejoué et vérifié dans cette passe, sur les sources réelles :

- **Les deux contre-exemples de la 2e passe sont fermés.**
  `{ jira: { toJSON: () => ({ apiToken: secret, toJSON: () => "safe" }) } }` → refusé,
  chemin exact `jira.apiToken`. `{ toJSON: () => fresh() }` avec objets neufs à chaque
  appel → l'inspection termine, sans faux positif.
- `toJSON` renvoyant un **tableau** portant un `Secret` → refusé, chemin `creds[1]`.
- `Secret` sous plusieurs niveaux de `toJSON` bénins → refusé, chemin `a.b.c.d.apiToken`.
- **Clé passée à `toJSON`** : index de tableau transmis en *chaîne* (`"0"`, `"1"`), comme
  `JSON.stringify` natif — comparé aux deux.
- Chemin signalé **vérifié contre la sortie JSON réelle** : sur chaque document où le
  masque est effectivement sérialisé, le chemin rendu par la garde, suivi dans
  `JSON.parse(JSON.stringify(doc))`, tombe bien sur le masque. 0 incohérence.
- Sous-graphe partagé (`{ a: shared, b: shared }`) → détecté ; cycle → refusé.
- Propriété nommée d'un tableau : ignorée par la garde *et* par `JSON.stringify` — cohérent.
- Round-trip chiffrement/déchiffrement fidèle ; l'enveloppe ne contient pas le jeton ;
  coffre altéré d'un octet, mauvaise clé, enveloppe étrangère, `v: 2`, base64 non canonique,
  clé de 16 octets → tous rejetés avec le bon `kind`.
- `encode` **asynchrone** refusé (`invalid_payload`), et **rien n'est écrit** (relecture →
  `absent`).
- **File d'`update()` réellement débloquée** : `update(() => new Promise(() => {}))` rend la
  main en ~30 s, l'écriture suivante aboutit et prend effet. 10 `update()` concurrents →
  10 incréments conservés.
- **`fsync` de `master.key` observé**, pas seulement lu : `fs/promises.open` instrumenté,
  `handle.sync()` appelé sur `master.key` comme sur le temporaire du coffre. Modes obtenus
  `master.key=600`, `config.enc=600`, dossier `700`, 0 fichier `.tmp` résiduel.
- Clé disparue → `key_missing` (jamais `absent`) ; clé illisible → `key_invalid` ;
  `read()` ne crée aucun fichier ; coffre de 0 octet → `corrupted` ; `update()` sur coffre
  illisible → erreur, `mutate` pas même appelé, coffre non écrasé ; dossier impossible à
  créer → erreur typée, aucune exception ne remonte.
- **Aucune fuite dans les messages** : les 1687 messages produits par la sonde ne
  contiennent ni le jeton, ni la clé (base64), ni le masque. `decode` qui lève une exception
  portant une sentinelle → message nettoyé. Accesseur qui lève → `invalid_payload` sans
  recopie.
- `lib/secret.ts` : `Object.keys` / `getOwnPropertyNames` / spread vides,
  `JSON.stringify` et `util.inspect(showHidden, depth:10)` rendent le masque et jamais la
  valeur, `revealSecret` exact, `isSecret` faux pour un sosie, **aucune méthode statique**
  sur la classe. Aucun `console.*` en dehors des commentaires. Aucun jeton en dur dans les
  trois fichiers.
- **Périmètre respecté** : `git status` ne montre que les trois fichiers attendus, tous
  untracked ; `git diff 860a48a` ne porte que sur les deux rapports QA précédents. Aucun
  débordement de domaine.

## Non couvert

- **Aucun test automatisé n'existe dans le dépôt** et aucun n'est ajouté par cette
  livraison. Tout ce qui précède vient de sondes jetables hors dépôt qui disparaissent avec
  la session : le prochain agent qui touche ce module repart sans filet. La doc l'assume au
  §Limites connues ; c'est la faiblesse structurelle de ce module, et la raison pour
  laquelle il a fallu trois passes pour le même défaut.
- **Fidélité à `JSON.stringify` : vérifiée, pas prouvée.** 8000 documents aléatoires + une
  vingtaine de cas construits à la main, sur Node v26.7.0 uniquement. Les formes non
  explorées incluent les `Symbol.toPrimitive`, les objets à prototype `null` porteurs d'un
  `toJSON` hérité, `Object.defineProperty` avec `enumerable: false` sur `toJSON`, et les
  interactions avec un `replacer` (le module n'en utilise pas). Un quatrième cas d'infidélité
  n'est pas exclu.
- **Transpilation ES2017 non rejouée.** La cible du projet est ES2017 (`tsconfig.json`) ;
  mes sondes ont compilé en ES2022 (champs privés natifs). Les passes précédentes avaient
  couvert ES2017 pour `lib/secret.ts` ; je ne l'ai pas revérifié, et `#value in candidate`
  abaissé en `WeakMap` est précisément le genre de détail qui change de comportement.
- **Concurrence inter-processus** non testée : la doc annonce l'absence de verrou de
  fichier, je n'ai pas mesuré ce que deux processus font réellement sur le même coffre.
- **Résistance à une coupure d'alimentation** non testée : l'atomicité du `rename` et
  l'effet réel du `fsync` sur le disque ne sont pas observables depuis un test utilisateur.
  J'ai vérifié que les appels sont émis, pas qu'ils tiennent leur promesse.
- **Console navigateur et tests** : non exécutés, les scripts n'existent pas
  (cf. tableau des vérifications). Aucune assurance n'est donnée sur ce plan.
